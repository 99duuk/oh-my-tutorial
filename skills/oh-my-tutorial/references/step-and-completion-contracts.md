# 단계와 완료 조건

## 단계 설계의 공통 정보

아래는 생각해야 할 정보다. 새 DSL, 고정 스키마, 모든 필드가 있는 거대한 타입을 반드시 만들라는 요구가 아니다. 기존 구조에 맞는 최소 모델을 선택한다.

| 정보 | 판단 |
|---|---|
| 안정적인 단계 식별자 | 이동·재시도·비동기 결과를 특정 단계와 연결 |
| 목표와 설명 | 이해하거나 수행할 과제 |
| 준비 조건 | 화면, 데이터, 권한, 선택 상태의 가용성 |
| 실행 맥락 | 특정 연습 항목·작업·데이터와의 연결 |
| 안내 대상과 조작 범위 | 필요한 경우에만 지정 |
| 진행 방식 | 설명 확인, 행동 성공, 결과 확인, 준비 완료 |
| 완료 근거 | 무엇을 성공으로 판단하는지 |
| 피드백 | 관찰할 변화와 의미 |
| 실패·재시도 | 실패 후 다음 시도의 조건 |
| 진입·이탈 처리 | 필요한 준비·취소·정리 |

## 진행 방식 선택

### 설명

사용자가 다음 버튼 등으로 진행한다. 중요 개념, 선택 기준, 작업의 전체 맥락에 적합하다. 자동으로 시간이 지나갔다고 이해했다고 판정하지 않는다.

### 조작

사용자의 행동이 실제로 성공했을 때 진행한다. 생성, 수정, 검색 실행, 그룹 배정, 상태 전환 등 결과가 있는 기능에 사용한다.

### 관찰·결과 확인

변화한 결과를 보여주고 사용자가 확인해서 진행하거나, 결과를 조회하는 의미 있는 조작과 연결한다. 내용을 읽고 이해했는지를 단순 화면 노출만으로 자동 인증하지 않는다.

### 준비 대기

필요한 준비 완료를 기다린다. 준비 시작, 완료, 실패, 취소 경로를 구분한다. 임의의 고정 지연은 실제 로딩 완료의 대체 근거가 아니다. 짧은 시각적 전환 지연을 쓰더라도 준비·성공 조건을 먼저 충족해야 한다.

### 마무리

달성한 목표, 실제 사용 경로, 필요한 다음 학습을 알려준다. 끝없는 다음 버튼 대신 완료·종료 동작을 제공한다.

## 실제 성공에 연결하는 위치

우선순위는 프로젝트의 기능 구조에 따라 선택한다.

1. 기존 실행 함수가 반환하는 성공 결과나 이미 존재하는 성공 이벤트.
2. 해당 기능의 결과를 소유하는 상태에서 확인할 수 있는 사후 조건.
3. 사용자 실행 이벤트와 결과 상태의 조합.

버튼의 DOM 클릭을 공통 성공 이벤트로 사용하는 것은 입력 검증, 서버 실패, 취소를 놓치기 쉽다. UI 동작 자체가 목표인 “패널 열기”라면 열린 상태 확인으로 충분하다.

사용자가 안내 버튼 대신 실제 메뉴, 단축키, 기존 제품 제어로 목표를 달성해도 같은 완료 근거로 반응한다. 예를 들어 실제 메뉴에서 목적 화면에 도착했으면 안내가 이전 화면에 남지 않게 한다. 반대로 모달이 닫혔다는 사실만으로 저장 성공을 추정하면 취소와 혼동된다. 성공 알림 역시 현재 연습 대상·요청과 연결됐는지 확인한다. UI 라이브러리의 다음·완료·닫힘 이벤트는 학습 성취와 구분한다.

| 목표 | 부족한 근거 | 적절한 근거 예시 |
|---|---|---|
| 예약 등록 | 저장 버튼 클릭 | 생성 성공 + 연습 예약 ID + 지정 시간 |
| 필터 적용 | 선택기 변경 | 지정 조건 반영 + 결과 갱신 완료 |
| 그룹에 항목 배정 | 드래그 시작 | 해당 항목이 대상 그룹에 포함됨 |
| 처리 요청 | 요청 버튼 클릭 | 프로젝트가 정의한 접수 성공과 작업 ID |
| 처리 결과 확인 | 접수 성공 | 해당 작업의 완료 결과를 조회함 |
| 안내 패널 열기 | 버튼에 포커스 | 패널이 실제 열린 상태 |

요청 접수와 실제 작업 완료를 구분한다. 사용자 목표가 접수라면 완료까지 기다릴 필요가 없고, 목표가 결과 확인이라면 접수만으로 끝내지 않는다.

학습 목표가 오류 식별·복구라면 해당 오류를 관찰하고 올바르게 수정한 사실이 학습의 완료 근거가 될 수 있다. 제품의 실패를 처리 성공으로 표시하지 않으면서도 오류 대응을 가르칠 수 있다. 일부 항목만 성공하는 기능은 반영된 항목과 실패 항목을 구분한다. 재시도 시 전체 작업을 다시 실행해 이미 반영된 항목을 중복 처리하지 않도록 기존 제품의 재시도 단위를 따른다.

## 목표에 맞는 정확도

“새 항목을 만드는 방법” 학습은 유효한 항목 생성으로 충분할 수 있다. “지정한 예약을 변경”하는 학습은 올바른 연습 예약의 값이 변경됐는지 확인해야 한다.

개수나 반복 횟수는 이유가 있을 때만 사용한다. 동일한 성공이 여러 이벤트로 들어온 것을 반복 수행으로 세지 않는다. 단순히 횟수 조건을 만족하려고 중복 데이터를 만들게 하지 않는다.

학습 시작 전부터 조건이 만족된 경우 정책을 선택한다.

- 상태를 관찰하는 목표: 이미 충족된 상태를 설명하고 확인 후 진행 가능.
- 직접 수행하는 목표: 격리된 준비 상태를 만들거나 새로운 수행을 기다림.
- 재방문: 기존 완료를 인정할지 다시 수행할지 명시.

“조건이 true”라는 이유만으로 사용자가 방금 과제를 수행했다고 단정하지 않는다.

## 비동기 결과와 단계 소유권

단계가 전환되거나 세션이 종료되면 이전 단계의 결과가 새 단계를 진행시키지 않아야 한다. 기존 취소·구독 구조를 활용해 다음 불변식을 지킨다.

- 결과에 따른 학습 전환은 해당 세션, 단계 진입 회차, 연습 대상과 일치할 때만 반영한다. 업무 결과 저장 자체의 조건으로 이 검사를 사용하지 않는다.
- 같은 성공은 한 번만 진행시킨다.
- 비동기 완료가 이전·종료·재시작 후 도착하면 현재 진행 상태를 바꾸지 않는다.
- 이탈한 단계의 대기, 타이머, 구독을 정리하고 대기 중 호출도 취소 또는 종료 상태로 정산한다.
- 재시작한 새 세션과 이전 세션의 같은 단계 ID를 혼동하지 않는다.

언어 중립적인 개념 예시:

```text
onSuccess(result, owner):
  if owner.session != currentSession: return
  if owner.entry != currentStepEntry: return
  if phase != awaitingAction: return
  if not matchesPracticeTarget(result): return
  if not satisfiesLearningGoal(result): return
  claimCompletionOnce()
  showFeedbackAndContinue()
```

실행 요청 시의 소유권을 결과와 연결한다. 결과 도착 시 현재 세션 값을 새로 붙이면 오래된 응답이 새 응답처럼 처리될 수 있다.

위 단계 진입 검사는 **이전 단계의 콜백이 현재 안내를 전환시키지 못하게 하는 기준**이다. 여러 단계에 걸친 업무 작업의 수명과 같지는 않다. 예를 들어 접수 단계에서 받은 `jobId`는 같은 세션의 결과 확인 단계로 전달할 수 있다. 다음 단계는 그 `jobId`의 현재 상태와 새 구독을 사용하며, 원래 요청 단계의 진입 번호가 다르다는 이유로 유효한 업무 결과를 버리지 않는다. 이미 완료된 작업에도 진입할 수 있으므로 완료 이벤트 한 번만 기다리는 구현을 피한다.

상태 읽기와 구독 사이에 결과를 놓치지 않도록 기존의 원자적인 상태 구독을 활용하거나, 구독한 뒤 현재 상태를 다시 읽고 중복 완료를 방지한다. 이전 단계 구독은 해제하되 새 단계의 대기를 위해 같은 업무 요청을 재실행하지 않는다. 세션 종료·재시작은 여전히 이전 세션의 결과가 새 학습을 진행시키지 못하게 한다.

## 결과 피드백과 전환

성공 직후 화면이 바뀌면 사용자가 결과를 놓칠 수 있다. 결과가 자체적으로 분명하면 바로 진행하고, 비교나 해석이 필요하면 확인 단계를 둔다.

예: 예약 생성 성공 후 생성된 일정 항목을 보여주고, 어떤 정보가 표시되는지 알려준다. 완료 이벤트 수신과 동시에 다른 메뉴로 이동시켜 결과를 가리지 않는다.

피드백을 위한 지연은 실제 완료 근거를 대체하지 않으며, 종료하면 지연된 전환도 취소한다.

## 이전·건너뛰기·분기

- 이전: 설명을 다시 보여주는지, 재수행할 준비 상태를 만드는지 결정한다. 실제 작업의 취소를 자동으로 의미하지 않는다.
- 건너뛰기: 기능이 필요하거나 사용자가 요청한 경우 제공한다. 수행 완료와 구분하며 다음 단계의 준비 조건을 충족하거나 안전한 경로로 이동한다.
- 분기: 실제 사용자 선택·역할·상태에 의해 필요한 경우만 만든다. 분기 후 합류 단계의 준비 조건도 확인한다.
- 종료: 대기 중 단계라도 가능해야 한다. 외부 요청 취소가 불가능하면 학습 종료와 실제 요청 상태를 구분한다.

상태를 설명하는 단계와 실제 동작을 실행하는 단계를 분리하면 재방문 시 원치 않는 재실행을 줄일 수 있다.

## 정의 검증

데이터로 단계를 관리한다면 잘못된 설정을 진입 전에 찾는 검증을 필요한 만큼 둔다.

- 중복 식별자, 존재하지 않는 다음 단계·분기.
- 행동 단계의 완료 조건 누락.
- 실행 가능한 학습의 준비 방법 누락.
- 불가능한 반복 횟수나 대기 설정.
- 학습 종료 경로 부재.

정적 정의 검사로 실제 화면의 준비 상태, 올바른 셀렉터, 실제 동작 성공까지 검증했다고 간주하지 않는다.
