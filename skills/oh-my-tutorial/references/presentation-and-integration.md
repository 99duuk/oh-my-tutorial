# 안내 표현과 프로젝트 연결

## 기존 구조 조사

먼저 라우터·메뉴·권한, 상태 소유자, 기능 실행 함수, 디자인 시스템, 기존 도움말·모달·팝오버를 확인한다. 기존 튜토리얼 기반이 있으면 필요한 개선으로 확장할 수 있는지 판단한다.

설치된 도구나 기존 컴포넌트로 요구를 만족할 수 있으면 우선 활용한다. 새 라이브러리는 실제 요구와 유지 비용을 비교해 선택한다. 여러 프레임워크를 지원하는 공통 엔진부터 만드는 것은 기본 작업이 아니다.

공개 도구의 선택 기준과 연결 예시는 [open-source-patterns.md](open-source-patterns.md)를 참고한다. 단계 표시와 업무 성공 판정을 서로 다른 책임으로 유지한다.

아래 책임을 구분한다. 프로젝트 규모에 맞게 합치거나 나눌 수 있다.

| 책임 | 소유할 내용 | 피할 결합 |
|---|---|---|
| 학습 내용 | 목표, 설명, 준비·완료 조건, 다음 경로 | 제품 함수마다 문구 하드코딩 |
| 진행 관리 | 세션, 현재 단계, 전환, 종료 | 모든 도메인의 상태를 공통 저장소에 복제 |
| 안내 표현 | 패널, 강조, 결과 피드백 | 안내 컴포넌트가 직접 업무 처리를 실행 |
| 기능 연결 | 준비 상태, 성공 결과, 화면 이동 | 기존 기능이 특정 학습 단계 ID를 알아야 함 |
| 연습 환경 | 데이터와 임시 상태의 소유권 | 실제 사용자 데이터 전체를 초기화 |

## 메뉴 진입점

튜토리얼 메뉴 요청에는 선택 가능한 학습 항목과 반복 실행 경로를 구현한다. 기존 서비스의 탐색 구조와 용어를 따른다.

학습 항목에는 사용자가 선택에 필요한 제목·목표·시작 동작을 제공한다. 설명이 긴 카드, 단계 수, 소요 시간, 아이콘은 실제 필요에 따라 추가한다. 측정하지 않은 소요 시간을 사실처럼 표시하지 않는다.

시작할 수 없는 항목은 필요한 조건과 해결 경로를 보여준다. 구현되지 않은 항목을 작동하는 학습처럼 노출하지 않는다. 관리자 전용 메뉴 체계를 우회해 사용자에게 새 권한을 주지 않는다.

## 안내 방식 선택

| 방식 | 적합한 상황 |
|---|---|
| 대상 가까운 설명·강조 | 버튼·입력·영역과 설명을 연결 |
| 옆 패널 | 실제 화면을 계속 보며 여러 행동 수행 |
| 화면 안의 안내 영역 | 조회·분석 등 결과와 설명을 함께 확인 |
| 모달 | 시작 맥락, 중요한 선택, 마무리 |
| 격리된 연습 화면 | 실제 작업과 분리가 필요한 체험 |
| 결과 비교 | 전후 상태나 선택에 따른 차이가 학습 목표 |

한 방식으로 모든 단계를 강제하지 않는다. 실제 기능과 연결된 체험을 만들되, 화면 복제가 필요한 경우에는 실제 업무 규칙·검증·표현을 재사용해 차이를 줄인다.

웹의 DOM 강조는 선택 가능한 구현이다. 네이티브 등 다른 환경에서는 그 환경의 화면·이벤트·수명주기에 맞게 연결한다. 현재 도구로 확인할 수 없는 플랫폼의 실행 검증을 했다고 보고하지 않는다.

### 학습 전용 제어

실제 제품에 없는 확인 버튼이나 퀴즈를 추가할 때는 그것이 학습 제어임을 구분한다. 가능한 한 안내 영역에 두고, 항목 옆에 필요하면 “학습용 확인”처럼 표시한다. 실제 메뉴에 없는 버튼을 눌러야 업무가 완료되는 것처럼 가르치지 않는다.

단순히 결과를 관찰하는 목표에는 결과를 보여주고 다음으로 진행하는 방식도 충분하다. 특정 항목을 찾거나 비교 값을 읽는 것이 목표일 때만 의미 있는 확인 행동을 선택한다. 클릭을 감지하기 쉽다는 이유로 가짜 업무 조작이나 반복 퀴즈를 만들지 않는다.

### 안내 카드와 시각적 완성도

먼저 기존 제품의 표면색·글자색·강조색, 여백, 둥글기, 그림자, 버튼, 포커스 표시를 읽어 재사용한다. 공개 예제의 색상이나 프레임워크를 제품 전체에 덮어쓰지 않는다. 카드의 외형은 진행 관리와 분리해 기존 디자인 컴포넌트로 교체할 수 있게 한다. 이 분리 방식은 [Onborda의 사용자 정의 카드 API](https://github.com/uixmat/onborda/blob/e865eb4089fb86b58ed75ca0e4742bcc59f81b31/src/types/index.ts)를 참고한다.

기본 카드 구성은 목표를 표현하는 제목, 짧은 행동 안내, 필요한 상태 피드백, 현재 단계에 맞는 제어다. 숫자가 유용하면 “안내 2/5”와 “과제 달성”의 의미를 구분한다. 첫 단계의 이전 버튼, 완료되지 않은 행동의 다음 버튼, 오류 중 완료 문구처럼 실제 상태와 맞지 않는 제어를 노출하지 않는다. 버튼을 비활성화했다면 무엇을 하면 진행되는지 함께 설명한다.

넓은 화면에서는 대상 옆에 배치하되 공간이 모자라면 반대편이나 고정 패널로 옮긴다. 작은 화면에서는 상단·하단 배치를 선택하고, 가상 키보드·고정 푸터·안전 영역 때문에 실제 조작과 종료 버튼이 가려지지 않는지 확인한다. 긴 번역문·200% 확대에서도 내용과 제어에 접근할 수 있어야 한다. CSS의 좁은 폭만 확인하고 모바일 입력 검증까지 완료했다고 하지 않는다.

강조 이동이나 성공 애니메이션은 결과를 알아보는 데 필요한 만큼만 쓴다. `prefers-reduced-motion`을 존중하고, 문구를 읽거나 성공을 인식하는 데 애니메이션 완료가 필수가 되지 않게 한다. 화면을 계속 점멸시키거나 자동 타이핑이 끝날 때까지 실제 조작을 막지 않는다.

## 대상 식별과 준비 상태

웹에서는 안정적인 기존 식별자, ref, 의미 있는 속성 또는 전용 안내 속성을 활용한다. 위치 기반 선택자, 번역된 텍스트, 임시 스타일 클래스에만 의존하면 화면 변경에 취약하다.

목록에서 특정 연습 항목을 가리킬 때는 연습 데이터의 안정적인 식별자로 연결한다. 첫 번째 행이 항상 대상이라고 가정하지 않는다. 의도한 화면 범위와 요소를 특정해 같은 선택자가 여러 곳에 있을 때 혼동하지 않게 한다.

공용 컴포넌트의 같은 속성이 다른 페이지에도 생기면 페이지 루트와 연습 데이터 ID로 범위를 좁힌다. 반응형 화면에서 데스크톱·모바일 요소가 함께 렌더링될 수 있으므로 숨겨진 후보를 제외한다. 실제 표시 후보가 둘 이상 남으면 첫 번째를 임의로 선택하지 말고 대상 범위를 수정한다. DOM이 교체된 뒤에는 이전 요소 참조와 좌표를 재사용하지 않는다.

다음은 구분한다.

- 대상이 아직 로딩되지 않음.
- 존재하지만 화면 밖에 있음.
- 숨겨진 팝업 안에 있음.
- 현재 상태·권한에서 존재하지 않음.
- 정의나 연결이 잘못돼 찾지 못함.

로딩·화면 준비 상태를 우선 활용하고, 그다음 필요한 만큼 관찰·측정한다. 계속 반복하는 폴링은 이유가 있을 때만 사용하고 세션 이탈 시 정리한다. 대기가 계속되면 상황에 맞는 재시도나 종료를 제공한다.

스크롤·팝업 전환 뒤에는 실제 배치가 안정됐는지 확인한 후 좌표를 읽는다. 한두 번의 animation frame 대기는 단순 배치 갱신에 쓸 수 있지만 긴 전환·가상 목록의 준비를 보장하지 않는다. 대상이 보인다는 것, 다른 요소에 가려지지 않았다는 것, 입력 가능한 상태라는 것은 별도로 확인한다. 필요한 경우 [browser-target.ts](../assets/browser-target.ts)를 적용한다. 사용 조건과 한계는 [공개 패턴 문서](open-source-patterns.md)에 있다.

## 강조와 조작 범위

강조하는 요소와 실제 조작을 허용해야 하는 요소는 다를 수 있다.

예를 들어 목록에서 그룹으로 항목을 옮기는 학습은 출발 영역, 드래그 이동, 도착 영역을 모두 사용할 수 있어야 한다. “출발 요소만 클릭 가능”한 제한으로 체험을 막지 않는다.

조작 제한은 학습 목표를 달성하는 데 필요한 정도로 선택한다. 제한을 쓰는 경우 다음을 확인한다.

- 현재 단계의 입력·팝업·결과 확인에 필요한 요소를 사용할 수 있는가?
- 허용된 영역에서 시작한 드래그가 영역 밖에서도 끝날 수 있는가?
- 진행 도중 단계가 전환돼도 포인터가 눌린 상태로 남지 않는가?
- 종료·재시도와 필수 탐색이 가능한가?
- 제한이 실제 권한이나 데이터 보호를 대신하고 있지 않은가?

보조 강조 영역은 참고용인지 조작 대상인지 명확히 구분한다. 제한이 필요 없는 탐색·비교 단계에는 과도한 포인터 차단을 적용하지 않는다.

## 키보드와 접근성

- 입력창, 선택기, 편집 가능한 영역에서는 문자를 학습 명령으로 가로채지 않는다.
- 기존 제품 단축키와 충돌하는 전역 문자 단축키를 만들지 않는다.
- Enter·Space가 폼 제출이나 기존 기능에 필요한 단계라면 학습 전환과 충돌하지 않도록 한다.
- 종료와 다음 등 안내 제어는 키보드로도 사용할 수 있게 한다.
- 안내 때문에 필요한 실제 조작 영역에 키보드 포커스가 갈 수 없게 만들지 않는다.
- 학습 종료 후 가능한 경우 시작한 제어로 포커스를 돌려준다.
- 실제로 모달인 UI에만 모달 의미와 포커스 제한을 적용한다. 뒤의 실제 화면을 조작하게 하는 안내에 무조건 모달 속성을 붙이지 않는다.
- 진행·결과 피드백을 보조 기술에도 전달하되 단계마다 과도한 반복 알림을 만들지 않는다.

## 화면 이동과 배치

단계가 다른 화면을 요구한다면 프로젝트의 기존 탐색 방식을 사용하고, 이동 성공과 화면 준비를 확인한다. 이동 실패를 무시한 채 잘못된 화면에서 조작을 요구하지 않는다.

튜토리얼 종료, 브라우저 뒤로 가기, 다른 메뉴 이동의 정책을 정한다. 사용자가 나가려는 동작을 무한히 원래 화면으로 되돌리는 흐름을 만들지 않는다.

설명 패널은 대상·필수 제어·결과를 가리지 않도록 배치한다. 스크롤 컨테이너, 화면 경계, 고정 내비게이션, 확대·축소, 팝업 레이어를 고려한다. 작은 화면에서는 설명 영역 배치를 바꾸거나 기존 레이아웃을 활용한다.

선택한 UI가 필요한 환경에서만 스크롤·리사이즈·요소 관찰을 연결한다. 정리 시 관찰자와 리스너를 해제한다.

## 기능 연결의 예시

```text
기존 기능: createReservation(input)
기존 기능의 결과: 성공 여부 + 생성된 예약
연결 계층: 현재 연습 대상과 학습 목적에 맞는 성공인지 판단
진행 관리: 유효한 세션에서 해당 단계 완료
안내 표현: 생성된 예약을 보여주고 결과 설명
```

기존 기능이 “예약 튜토리얼의 3번 단계”를 직접 알도록 만들지 않는다. 기존 이벤트·구독·의존성 주입·콜백 등 프로젝트에 맞는 가장 작은 연결을 사용한다.

조회 기능의 원시 데이터 이벤트와 실제 화면 반영은 다를 수 있다. 예를 들어 모델이 응답을 알린 뒤 화면에서 요청 버전을 확인해 오래된 결과를 버리는 구조라면, 원시 응답만으로 조회 학습을 완료시키지 않는다. 화면이 채택한 결과를 알려주는 작은 이벤트나 실제 표시 상태를 사용한다. 응답을 받았다는 것과 사용자가 그 결과를 볼 수 있다는 것을 연결해서 확인한다.

단계 이탈·종료의 비동기 처리 기준은 [step-and-completion-contracts.md](step-and-completion-contracts.md)를 따른다. 데이터 소유권은 [practice-environment-and-lifecycle.md](practice-environment-and-lifecycle.md)를 따른다.
