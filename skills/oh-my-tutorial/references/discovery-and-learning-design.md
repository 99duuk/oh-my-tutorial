# 조사와 학습 설계

## 조사 순서

목표 사용자와 대상 기능을 중심으로 필요한 코드만 조사한다. 아래 순서는 발견 결과에 맞춰 조정한다.

1. 프로젝트 지침, 실행 명령, 라우트·메뉴·권한 구조를 확인한다.
2. 대상 화면에서 대표 작업 하나를 실제 실행 함수와 결과 표시까지 추적한다.
3. 상태 저장소·서버 호출·검증·데이터 준비·오류 처리·종료 처리를 확인한다.
4. 업무 문서와 기존 도움말에서 개념, 의도, 역할별 차이를 찾는다.
5. 기존 튜토리얼·팝오버·모달·테스트 도구를 재사용할 수 있는지 확인한다.
6. 가능한 경우 실제 화면을 실행해 코드에서 추정한 흐름을 확인한다.

코드에 함수가 있다는 것, 사용자가 그 기능에 접근할 수 있다는 것, 해당 사용자가 첫 학습에서 그 기능을 배워야 한다는 것은 각각 다른 판단이다.

## 조사 산출물

아래 내용을 짧은 작업 메모나 프로젝트에 맞는 설계 문서로 정리한다. 문서 파일의 별도 생성은 사용자 요청과 프로젝트 관례를 따른다. 이 양식을 채우는 것이 구현을 대신하지 않는다.

```text
대상 사용자 / 역할:
대상 메뉴·업무와 범위:
학습 후 혼자 할 수 있어야 하는 일:
실제 시작 조건과 최종 결과:
핵심 개념과 판단 기준:
화면 → 실행 함수 → 결과 표시의 근거:
필요한 데이터·권한·외부 서비스:
기존 안내·디자인·검증 도구:
확인된 사실 / 설계 가정 / 확인이 필요한 판단:
이번 범위에서 제외되는 기능:
```

근거는 실제 파일·심볼·문서 또는 관찰 결과에 연결한다. 프로젝트에 없는 API나 권한을 설계 사실처럼 적지 않는다.

## 짧은 요청 처리

사용자가 “이 메뉴를 튜토리얼로 만들어줘”라고 하면 다음을 먼저 추론한다.

- 현재 대화나 선택한 화면에서 대상이 명확하면 그대로 사용한다.
- 대표 사용자와 목표가 명확하면 초보자가 한 가지 주요 결과를 얻는 흐름을 우선 설계한다.
- 메뉴가 너무 크면 먼저 주요 흐름과 후보 범위를 제시하고 독립적으로 진행 가능한 조사를 계속한다.
- 대상이나 중요한 업무 의도가 여러 가지로 갈리고 자료로 결정할 수 없을 때만 질문한다.
- 샘플 데이터 생성 방법, 라이브러리 선택, 이벤트 위치처럼 코드로 판단할 수 있는 사항을 장문의 설문으로 묻지 않는다.

기본안은 결정의 근거와 함께 남긴다. 불확실한 사실을 확정하거나, 실제 업무 역할을 임의로 바꾸지는 않는다.

## 목표를 학습 항목으로 바꾸기

좋은 목표는 사용자의 결과를 표현한다.

| 기능 목록 표현 | 학습 목표 표현 |
|---|---|
| 예약 버튼, 시간 선택기, 저장 버튼 | 빈 시간에 예약을 등록하고 일정에서 확인한다 |
| 상태 필터, 기간 필터, 차트 | 원하는 범위로 분석 대상을 좁히고 두 기간의 차이를 확인한다 |
| 결재자 목록, 요청 버튼 | 업무 규칙에 맞는 결재 경로를 정하고 요청 상태를 확인한다 |
| 레이어, 정렬, 내보내기 | 두 요소를 배치하고 원하는 형식으로 결과를 얻는다 |

실제 기능이 지원하는 결과만 목표로 삼는다. “올바른 판단을 이해했다”는 목표는 단순 클릭 횟수로 증명되지 않는다. 필요한 경우 결과 해설, 비교, 짧은 재수행으로 확인하되 시험 기능을 일괄 추가하지 않는다.

학습 항목 하나는 가능한 한 독립적으로 시작·종료·재시작할 수 있게 한다. 다른 항목의 완료가 꼭 필요하면 그 의존성을 명시하고 필요한 초기 상태를 준비한다.

## 학습 구성 선택

| 구성 | 선택 근거 | 과도한 적용을 피할 점 |
|---|---|---|
| 대표 작업 따라 하기 | 작업 순서를 처음 배워야 함 | 모든 예외와 설정을 한 번에 넣지 않음 |
| 기능·개념 상세 안내 | 개념이나 선택지가 복잡함 | 기능 이름의 사전처럼 만들지 않음 |
| 현재 맥락의 연습 | 실제 사용 순간 짧은 도움이 유용함 | 현재 작업에 미치는 영향을 확인 |
| 독립 과제 목록 | 설정·학습 항목의 순서가 무관하며 나눠 수행 가능 | 임의 순서를 강요하거나 목록을 채우려고 과제를 만들지 않음 |

단순한 기능은 한 항목으로 끝나도 된다. 서비스 전체의 카드 수, 첫 화면의 열 수, 단계 수를 원본 사례에 맞추지 않는다.

순서가 필요한 작업 안에서는 선형 흐름이 적합하다. 서로 독립적인 목표는 메뉴에서 따로 선택하게 하고, 목록과 항목 내부의 진행 순서를 구분한다. 실제 역할·선택·상태가 경로를 바꾸면 의미 있는 분기만 반영한다. 존재하지 않는 역할을 시뮬레이션하려고 실제 권한을 우회하지 않는다. 조건이 맞지 않는 학습은 가용 조건과 대안을 보여준다.

자동 노출이 요청됐다면 페이지 로드 자체보다 해당 기능의 사용 맥락에 연결한다. 환영 안내·학습 목록·힌트를 동시에 띄우지 말고 한 번에 한 가지에 집중하게 한다. 자동 재노출 억제와 사용자가 메뉴에서 직접 다시 시작하는 동작은 별개로 처리한다. 이 구성 판단은 [Usertour의 작성 기준](https://github.com/usertour/skills/blob/a6f41de1e69bb3bb3a25c29314e64e33d48eacf6/skills/usertour-content-authoring/references/patterns.md)을 각색했다. 고정 단계 수나 서비스 연결은 가져오지 않는다.

## RPG식 학습의 구체적인 적용

### 필요한 순간에 설명

새로운 개념은 그 개념을 사용하는 첫 행동 가까이에 배치한다. 첫 화면에서 서비스 전체 용어를 먼저 암기시키지 않는다. 사용자가 이미 알고 있는 간단한 행동은 반복 설명하지 않는다.

### 작은 과제와 관찰 가능한 결과

과제는 현재 상태에서 달성 가능해야 한다. 수행 후 결과가 화면 밖에 있다면 해당 결과를 보여주는 단계를 포함한다. “저장했으니 다음” 대신 생성된 항목이나 상태 변화를 확인하게 한다.

### 안내를 줄이는 선택

처음에는 구체적으로 안내하고, 반복되는 행동은 짧은 목표만 제시하는 방식이 유용할 수 있다. 기능이 단순하거나 반복이 불필요하면 추가 과제를 만들지 않는다. 학습한 내용을 실제로 써볼 기회가 필요할 때만 재수행을 넣는다.

### 실수에 대한 피드백

기존 폼 오류와 도메인 검증 메시지를 먼저 활용한다. 튜토리얼 메시지는 무엇을 수정하면 진행할 수 있는지 보완한다. 실수를 처벌하거나 이미 수행한 모든 단계를 자동 초기화하지 않는다.

## 단계 문구 작성

내용은 필요한 만큼 다음 요소를 연결한다.

```text
상황 또는 이유: 예약 가능한 시간을 찾아야 합니다.
할 일: 비어 있는 시간 하나를 선택하세요.
기대 결과: 선택한 시간으로 예약 입력 화면이 열립니다.
```

세 문장을 모든 단계에 강제로 반복하지 않는다. 짧은 단계는 한두 문장으로 충분할 수 있다.

- 화면에서 실제 사용하는 용어와 버튼 이름을 따른다.
- 설명 단계에서는 조작이 필수인 것처럼 쓰지 않는다.
- 조작 단계에서는 무엇을 어디서 어떻게 하는지 알려준다.
- 시뮬레이션, 조회, 실제 변경의 차이는 사용자의 판단에 필요한 위치에서 표시한다.
- 아직 지원하지 않는 기능이나 백엔드 동작을 약속하지 않는다.
- 내부 이벤트 이름, 상태 저장소, API 경로는 제품 사용자에게 노출하지 않는다.

## 설계 검토 질문

- 이 순서가 화면 배치가 아니라 실제 사용자 목표에서 나왔는가?
- 지금 설명하는 개념이 다음 행동에 필요한가?
- 사용자가 직접 달성하거나 확인할 의미 있는 결과가 있는가?
- 모든 기능을 넣느라 대표 작업의 흐름이 끊기지 않는가?
- 학습을 마치면 실제 기능의 위치와 사용 상황을 알 수 있는가?
- 해당 도메인의 판단이 예제의 단어 치환으로 축소되지 않았는가?
