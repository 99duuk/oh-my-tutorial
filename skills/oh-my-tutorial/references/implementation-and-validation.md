# 구현과 검증

## 구현 순서

1. 조사 결과를 바탕으로 요청 범위, 대표 학습 경로, 준비·완료 조건을 정한다.
2. 기존 구조를 활용할 지점과 작은 기능 연결을 선택한다.
3. 메뉴에서 시작해 실제 수행, 결과 확인, 종료까지 대표 경로를 연결한다.
4. 이 경로에서 얻은 결과로 설계를 수정하고 요청 범위의 나머지 학습을 구현한다.
5. 필요한 실패·중단·재시작과 기존 기능 회귀를 검증한다.

이 순서는 점진적으로 검증하기 위한 것이다. 매 단계마다 승인을 요청하거나 대표 경로만 만들고 전체 요청을 완료했다고 보고하는 절차가 아니다.

프로젝트 지침과 기존 명령을 사용한다. 문서 변경에 무관한 애플리케이션 테스트를 반복하지 않고, 변경과 연결된 의미 있는 검증을 선택한다. 기존 테스트 도구가 있으면 우선 활용한다.

## 산출물

요청 범위에 맞춰 다음을 구현한다.

- 학습 메뉴 또는 기존 메뉴의 학습 진입점.
- 목표와 실제 기능이 연결된 학습 내용.
- 필요한 진행 관리·안내 UI·기능 연결.
- 필요한 연습 환경과 정리 처리.
- 변경에 적절한 검증과 실행 방법.

설계 근거와 검증 결과는 사용자가 검토할 수 있는 형태로 남긴다. 별도 문서 파일은 프로젝트 관례나 요청에 맞춰 생성한다. 기술과 규모에 맞지 않는 관리자 시스템, 분석 수집, 다중 프레임워크 엔진은 기본 산출물이 아니다.

## 학습 품질 검증

학습 항목별로 다음을 확인한다.

| 질문 | 확인할 근거 |
|---|---|
| 사용자 목표에서 나온 흐름인가? | 목표와 단계·결과의 대응 |
| 설명이 실제 기능과 일치하는가? | 코드·문서·실행 결과 |
| 직접 수행이 적절히 포함됐는가? | 적합한 단계의 사용자 행동과 성공 확인 |
| 결과를 알아볼 수 있는가? | 생성 항목, 상태 변화, 비교 결과 또는 해설 |
| 단계별 과제가 달성 가능한가? | 준비 상태와 수행 경로 |
| 학습 후 실제 사용 위치를 아는가? | 마무리와 실제 메뉴 연결 |

관찰 학습을 억지로 데이터 변경 과제로 바꾸지 않는다. 반대로 생성·편집을 배우는 요청을 읽고 넘기는 설명만으로 완료하지 않는다.

## 동작 검증 행렬

해당 기능의 실패 가능성과 영향에 맞춰 관련 행을 선택한다. 존재하지 않는 기능을 테스트하기 위한 구현을 추가하지 않는다.

| 상황 | 기대 동작 |
|---|---|
| 메뉴에서 시작 | 올바른 맥락과 초기 상태로 진입 |
| 정상 수행 | 학습 목표의 성공을 확인하고 한 번만 진행 |
| 입력 오류·실행 실패 | 진행하지 않고 수정·재시도 가능 |
| 같은 성공 이벤트 반복 | 다음 단계까지 연쇄 통과하지 않음 |
| 다른 작업의 성공 이벤트 | 현재 학습을 완료시키지 않음 |
| 접수와 결과 확인 사이에 작업 완료 | 같은 작업 ID의 저장된 상태를 확인하며 이벤트를 놓쳐 멈추거나 재요청하지 않음 |
| 화면 이동 중 작업 완료 | 제품의 작업 상태·이력은 갱신되고 학습은 정한 종료·복귀 정책을 따름 |
| 일부 성공 후 재시도 | 실제 반영 상태를 보존하고 제품이 정한 실패 항목만 다시 처리 |
| 시작 전부터 충족된 조건 | 관찰·직접 수행 정책에 맞게 처리 |
| 느린 로딩·요소 부재 | 준비 상태와 재시도·종료 경로 제공 |
| 이전·건너뛰기·분기 | 다음 단계의 준비 조건 유지 |
| 준비·실행 대기 중 종료 | 늦은 결과가 학습을 다시 열지 않음 |
| 종료 후 재시작 | 새 세션에서 목표를 다시 수행 가능 |
| 화면 이탈·제거 | 리스너·임시 제어·대기 처리 정리 |
| 현재 작업에서 체험 | 기존 작업과 정해진 변경 유지 정책 보존 |
| 튜토리얼 없이 기존 기능 사용 | 기존 검증·권한·성공·오류 처리 유지 |

웹 UI에서 관련되는 경우 추가 확인:

- 설명·강조가 필수 제어와 결과를 가리지 않음.
- 폼 입력, 키보드 제어, 팝업, 스크롤을 실제로 사용할 수 있음.
- 드래그 시작과 도착을 모두 수행할 수 있음.
- 화면 크기 변화에서도 종료와 필요한 행동이 가능함.
- 키보드 포커스와 모달 의미가 실제 상호작용과 일치함.
- 실제 메뉴·단축키로 진행해도 안내가 현재 맥락을 따라감.
- 숨겨진 반응형 복제 요소, 모달 전환, 대상 DOM 교체를 올바르게 처리함.
- 안내의 다음·닫기·오버레이 클릭·방향키가 수행 조건을 우회하지 않음.
- iframe·포털을 쓰면 실제 대상 document와 레이어에서 동작함.

## 안내가 안 보이거나 진행이 멈출 때

임의 지연을 늘리기 전에 다음 순서로 관찰한다. 해당 프로젝트에 존재하는 조건만 확인한다.

1. 진입: 경로·사용자 역할·대상 데이터가 학습 조건과 일치하는가?
2. 노출: 자동 노출 조건·이전 닫힘·다른 활성 안내 때문에 억제됐는가? 수동 다시 시작도 잘못 막았는가?
3. 준비: 현재 세션과 단계 진입 회차가 유효하며 필요한 화면·요청이 준비됐는가?
4. 대상: 올바른 document·페이지 범위에서 후보가 몇 개이고 실제 표시 후보는 몇 개인가?
5. 표시: 좌표·스크롤·포털·상위 레이어·가상 키보드에 가려졌는가?
6. 진행: 기대한 성공의 연습 대상·요청 ID가 실제 결과와 일치하며 그 결과가 화면에 반영됐는가?

개발용 진단에는 단계 키, 준비 상태, 후보 수, 대기 시간, 마지막 실패 이유 정도를 남긴다. 사용자 데이터 전체를 로그로 내보내거나 진단 정보를 제품 안내 문구로 노출할 필요는 없다. Usertour의 조건 기반 진단 접근을 일반화한 것으로, 별도 분석 서비스나 SDK 설치를 요구하지 않는다.

## 테스트 선택

정적 검사로 타입, 빌드, 설정을 확인한다. 상태 관리가 복잡하면 성공·실패·중복·늦은 결과·종료 같은 동작 불변식을 검증한다. UI와 실제 기능 연결은 가능한 실행 환경에서 확인한다.

설명 문자열, 제목, 함수 이름이 예상과 같은지만 검사하는 테스트를 학습 동작 검증으로 취급하지 않는다. 새 테스트 기반을 만들기보다 기존 도구나 작게 격리한 실행 검증으로 확인할 수 있는지 먼저 판단한다.

테스트용 환경에서 기능을 시뮬레이션한 경우 실제 서버·실제 사용자 경험까지 검증한 것으로 확대하지 않는다. 실행 환경이 없으면 코드로 확인한 범위와 실행하지 못한 경로를 명확히 보고한다.

### 테스트 도구가 없는 작은 프로젝트

기존 실행 명령과 사용 가능한 브라우저 검증을 먼저 확인한다. 렌더링이 필요 없는 DOM 이벤트·상태 검증이라면 프로젝트와 호환되는 DOM 실행 도구를 임시 환경에 설치해 실제 애플리케이션 모듈과 HTML을 실행할 수 있다. 특정 도구를 모든 프로젝트의 필수 의존성으로 추가하지 않는다.

임시 도구를 사용하면 설치 위치·버전, 준비 명령, 실행 명령, 정리 범위를 함께 남긴다. 제품의 의존성이나 lockfile을 의도치 않게 변경하지 않는다. 검증 후 임시 의존성을 제거한다면 남겨둔 테스트의 재실행에 필요한 준비 단계를 명시한다. 일반 테스트 명령이 제거된 임시 도구에 의존하게 만들지 않는다.

DOM 실행 검증은 실제 렌더링, 요소 좌표, 모바일 배치, 스크린리더 동작을 증명하지 않는다. 해당 확인이 필요하면 실제 브라우저에서 별도로 수행하고 검증 결과를 구분한다.

## 도메인 독립성 검증

새 스킬이나 큰 개정본은 성격이 다른 사례로 판단을 확인한다. 모든 사례를 구현해야 한다는 뜻은 아니다. 시간이 허용하는 실제 적용과 설계 검토를 구분한다.

- 입력·검증 중심: 생성 성공과 입력 오류.
- 업무 흐름 중심: 상태 전환, 역할, 비동기 처리.
- 조회·분석 중심: 조건·결과 일치와 비교.
- 조작 도구 중심: 모드, 드래그, 반복 작업.

다른 도메인에서 원본 사례의 용어만 바꾼 설계가 나오면 목표 도출과 완료 조건 규칙을 수정한다. 실제 사용에서 확인한 문제를 근거로 좁게 개선하고, 상상 가능한 모든 예외를 공통 강제 규칙으로 쌓지 않는다.

## 결과 보고

사용자가 바로 검토할 수 있도록 다음을 간결하게 보고한다.

```text
진입 방법:
구현한 학습 범위와 직접 수행할 내용:
연습 데이터와 변경 유지·정리 방식:
수행한 검증:
확인하지 못한 실행 경로 또는 필요한 외부 조건:
```

완료 여부는 실제 구현과 검증에 맞게 표현한다. 예시 데이터 준비, 서버 연결, UI 체험이 남아 있으면 그 상태를 숨기지 않는다. 사용자에게 공통 기능의 누락을 계속 지시받기보다 도메인별 학습 품질을 조정할 수 있는 상태를 목표로 한다.
